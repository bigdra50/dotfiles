## 開発スタイル

TDD で開発する（探索 → Red → Green → Refactoring）。
KPI やカバレッジ目標が与えられたら、達成するまで試行する。

自分が作った skill・プロンプト・ドキュメントの出来を確かめるときは、自分で読み返して判断せず、会話の文脈を持たない新しい subagent に読ませる。
書いた本人は意図で行間を補って読むため、欠落に気づきにくい。
編集中の CLAUDE.md や導入済みの skill を評価させる場合、subagent にも旧版が読み込まれているので、渡したファイルを優先するよう伝える。

## コード設計

- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つ
- 静的検査可能なルールはプロンプトではなく、その環境の linter か ast-grep で記述する

## リポジトリ管理

### ghq

ローカルリポジトリは `ghq` で管理している。

```bash
ghq root                   # リポジトリルート取得
ghq list                   # ローカルリポジトリ一覧
ghq list | rg <keyword>    # リポジトリ検索
ghq get <repo>             # clone
```

別リポジトリの参照やcloneが必要な場合は `ghq` を使う。
`bigdra50/dotfiles` の置き場所は `~/dev/github.com/bigdra50/dotfiles` で固定している。
ghq root がこの外にあるマシンでは、`ghq list` から見つからない。

### 他人と共有するリポジトリ

他人と共有するリポジトリ（OSS、fork、業務のチームリポジトリ）に自分だけが使うファイル（`mise.local.toml` など）を置くときは、リポジトリの除外ファイルに追記する。
追跡されている `.gitignore` や `mise.toml` は、自分の都合で書き換えない。
worktree と submodule の `.git` はファイルなので、除外ファイルのパスは `git rev-parse --git-path info/exclude` で調べる。
除外ファイルは clone ごとの設定で push されないため、相手のリポジトリに差分が残らない。

### 個人で新しく作るリポジトリ

個人アカウント（bigdra50）で新しく作るリポジトリには、gitleaks で秘密情報を検査する pre-commit hook を入れる。
`~/dev/github.com/bigdra50/dotfiles` から `.pre-commit-config.yaml` と `.gitleaks.toml` の両方を写し、`uvx pre-commit install` で有効にする。
`.gitleaks.toml` には業務の識別子を止める独自ルールがあるため、`.pre-commit-config.yaml` だけを写すと gitleaks の標準ルールしか適用されない。
commit に入った秘密情報は履歴を書き換えないと消せないため、push 時ではなく commit 時に止める。

## 破壊的操作

ツールやセットアップスクリプトが上書き前に退避したファイル（`*.backup*`、`*.detached.*`、`*.pre-*`、`*.orig`、`*.bak` など）は、中身を会話に示してから削除する。
長いファイルやディレクトリなら、現行版との差分で足りる（現行版が無ければファイル一覧）。
認証情報やトークンを含みうるファイルは値を伏せ、キー名と差分の有無だけを出す。
現行版に無い内容が見つかったときは、消す前にユーザーへ確認する。
自分で作ったファイルではないため、読まずに消すと元の内容を確かめる手段がなくなる。

## スキル作成

新しい skill の置き場所は、使う範囲と公開してよいかで決める。

| 使う範囲                         | 置き場所                           |
| -------------------------------- | ---------------------------------- |
| 特定のリポジトリでの作業だけ     | そのリポジトリの `.claude/skills/` |
| 自作ツールと一緒に配る           | そのツールのリポジトリ             |
| 複数のリポジトリ（公開してよい） | `bigdra50/skills` のカテゴリ配下   |
| このマシンだけ（非公開）         | `~/.claude/skills/` に直接置く     |

`bigdra50/skills` に作るときは、そのリポジトリの CLAUDE.md（命名、英語で書くこと）と README（グローバルとプロジェクト単位のどちらで入れるか）に従う。
グローバルに入れるものは `~/dev/github.com/bigdra50/dotfiles/.apm/apm.yml` に登録し、反映はファイル冒頭のコメントの手順で行う。
`~/.claude/skills/` に直接置いたものは apm が管理外として残すが、マシン間では同期されない。
表のどの行にも当てはまらないとき（非公開のまま複数のマシンで使う skill など）や、複数の行に当てはまるときは、作り始める前にユーザーへ確認する。
後から移すと、apm.yml の登録や skill 内のパス参照が壊れやすい。

## Output Style

### 作業完了時のASCII図解

実装完了・作業完了後、変更内容をASCII図で視覚的に示す。

作業内容に応じて適切な図を選択：

| 作業内容              | 図の種類         |
| --------------------- | ---------------- |
| API・処理フロー実装   | シーケンス図     |
| クラス・型の追加/変更 | クラス図         |
| モジュール構成変更    | コンポーネント図 |
| 状態管理実装          | 状態遷移図       |
| データ構造変更        | ER図             |
| パイプライン・CI/CD   | フロー図         |

図解のルール：

- ASCII文字のみ使用（`+`, `-`, `|`, `>`, `*` 等）
- 変更箇所が明確にわかること
- 過度に巨大な図は避け、要点に絞る

### ランダムASCIIアート

作業完了時、低確率（体感5回に1回程度）で遊び心のあるASCIIアートを添える。

方針：

- 図解の代わりではなく、図解に加えてオマケとして出す
- CLIカルチャーのミーム、名言、小ネタなど自由に
- 短く、3〜6行程度に収める
- 作業内容や状況に合ったものを選ぶとなお良い

### 専門用語・略語の初出説明

ユーザーが普段使わない略語・専門用語をセッションで初めて使うときは、その直後に概要を 1 行添える。

- 同一セッション内の 2 回目以降は不要
- ユーザーの専門分野で自明な語には付けない（冗長回避）

## マシンローカル import

git 管理外のマシン固有メモリを読み込む。
ファイルが無いマシンでは import は無視される。
