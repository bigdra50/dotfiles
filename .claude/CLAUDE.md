## 開発スタイル

TDD で開発する（探索 → Red → Green → Refactoring）。
探索の終わりに、満たすべき性質（プロパティ）を述語で列挙する。
Red は、その性質をテストにするところから始める。
KPI やカバレッジ目標が与えられたら、達成するまで試行する。

## コード設計

- コントラクト層（API/型）を厳密に定義し、実装層は再生成可能に保つ
- コントラクト層には、性質（事前条件、事後条件、不変条件）も書く。実装の再生成は、この性質と型を入力にして行う
- 静的検査可能なルールはプロンプトではなく linter か ast-grep で記述する

## 形式検証容易性

仕様と実装は、テスト容易性に当たる「形式検証容易性」を持つ。
検証を後付けすると、性質は推測になる。
検証の範囲は狭まり、手間が増える。
仕様と実装は、書く時点から、性質を述語で書けて機械的に確かめられる形にする。

### 仕様

- 性質は、入力の定義域、事前条件、事後条件、不変条件の述語で書く
- 「正しく」「速く」のような、基準を示さない語で性質を書かない。量と境界を書く
- 性質は公開インターフェースの語彙だけで書く。実装の内部に触れない
- 状態を持つ機能は、状態の一覧と許される遷移を書く
- 決めない部分は「未規定」と明記し、暗黙の既定を残さない
- 検証の前提（入力の範囲、環境の仮定）は、性質と並べて書く
- 性質を述語で書けない機能は、仕様が足りない。実装へ進まず、先に仕様を補う

### 実装

- 不正な状態を型で表せなくする（直和型、非空のコレクション、範囲付きや単位付きの型）
- 境界で入力を型へ変換する。内部の関数は、変換後の型だけを受け取る（parse, don't validate）
- 全域関数にする。想定内の失敗は戻り値の型に含め、例外や null で部分性を隠さない
- 境界で事前条件を検査する。内部の関数は、それを前提に書く
- 状態遷移は enum と遷移表で書く。boolean の組み合わせで状態を表さない
- ループと再帰には、減少する量を決めて停止の根拠にする
- 関数は、契約を 1 文で書ける大きさに保つ
- 純粋関数と不変データ（design-principles.md の原則）が、形式検証容易性を支える

### 性質の置き場所

| 性質 | 置き場所 |
| --- | --- |
| 値の定義域、状態の組み合わせ | 型 |
| 事前条件、事後条件、不変条件 | 境界の検査（assert、引数検証）、プロパティベーステスト |
| 状態遷移、並行の性質 | 遷移表、必要ならモデル検査 |
| 停止 | ループと再帰の減少する量 |

プロパティベーステストのフレームワーク（Hypothesis、proptest、FsCheck）がある環境では、性質のテストをそれで書く。
例示テストは、性質の具体例として置く。
契約や証明のツール（Kani、Dafny、TLA+）が使えるなら使う。
型と契約は、性質を守るのに要る分だけ増やす。

## リポジトリ管理（ghq）

ローカルリポジトリは `ghq` で管理している。

```bash
ghq root                   # リポジトリルート取得
ghq list                   # ローカルリポジトリ一覧
ghq list | rg <keyword>    # リポジトリ検索
ghq get <repo>             # clone
```

別リポジトリの参照やcloneが必要な場合は `ghq` を使う。
