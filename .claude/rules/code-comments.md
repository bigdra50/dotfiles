# コードコメントルール

何をどこに書くかの分担（t_wada の標語を骨格にした整理）:

| 場所 | 書くもの |
| --- | --- |
| コード | How（実装そのもの） |
| テストコード | What（仕様の表明） |
| コミットログ | Why（この変更をした理由） |
| コードコメント | Why not（あえてしなかったこと）+ 行に張り付くべき Why |

コメントの本質は「コードに表れない書き手の意図」を残すこと。
コードから自明なことは書かない。
コミットログの Why は変更単位に紐づくが、行そのものに張り付いていてほしい Why（制約・根拠・不変条件）は blame を掘らせず、コメントとして行の隣に置く。

## コメントに書くもの

- あえてやらなかったこと（why not）とその理由。言語化しないと「知らずにやらなかった」と区別できず、レビュワーの不要な指摘や後続開発者の誤った参考を招く
- 設定値・閾値の根拠（例: 「正常時 5 秒を超えないため timeout は 5 秒」）
- 条件分岐やエラーハンドリングの有無の理由（例: 「zoneinfo セット済みでエラーは発生しないためハンドリングしない」）
- 単位、境界の包含/排他、null の意味、不変条件（例: 「このリストは常に1要素以上」）
- ビジネス要件・技術的制約（例: 「SEO 要件によりタイトルは 30 文字以内」）
- モジュール間の制約・依存関係（例: DB への保存形式など他モジュールに影響する決定）

## 書かないもの

- 動作の言い換え（「配列をループする」）。コードが既に語っている
- 命名の改善で消せる説明。コメントより先にコードを直す
- 期限・理由のない TODO。技術的負債は FIXME + 理由で残す
- ライブラリの一般的な使い方

## 判断基準

「初めて見る人がここで困るか」。
困るなら書く、困らないなら書かない。
コメントの最大のリスクは実装との乖離なので、書いた分だけ保守責任を負う。
コードを変更したら周辺コメントも更新する。
